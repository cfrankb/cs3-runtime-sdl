# Audit: src/shared/CRC.h
Date: 2026-11-17

## Summary
CCRC is a verbatim copy of the classic gzip/zlib appendix reference implementation and is algorithmically correct: reflected CRC-32/ISO-HDLC (poly 0xEDB88320 reflected, init 0xFFFFFFFF, final XOR 0xFFFFFFFF), matching PNG chunk CRCs and zlib's `crc32(0L, buf, len)` exactly. The most important issue is not correctness but redundancy: `zlibstatic` is already linked into `shared_lib` and `zlib.h` is already included by every translation unit that uses CCRC, so the entire 65-line class (plus its per-instance lazy 2 KB table) can be replaced by `zlib crc32`. Remaining findings are integer-width hygiene (`unsigned long` return, `int len` silently accepting negatives via caller size_t narrowing) and minor perf/const issues. Counts: 0 Critical, 0 High, 3 Medium, 3 Low.

## Findings

### Medium
- L22-86: [shrink] The whole class duplicates already-linked platform functionality: `shared_lib` links `zlibstatic` (src/shared/CMakeLists.txt:33) and Frame.cpp:26 / PngMagic.cpp:21 already `#include <zlib.h>`; zlib's `crc32(0L, buf, len)` computes the identical CRC-32 (same poly/init/xorout) with a shared, once-built, possibly hardware-accelerated table. Fix: delete CRC.h and call `crc32(0L, buf, len)` at the 8 call sites (Frame.cpp:354/381/396/405, PngMagic.cpp:227, t_pngmagic.cpp:352-354), or at minimum keep the header but make it a one-line wrapper.
- L32-34: [integer] Return type `unsigned long` is 32-bit on LLP64 (Windows) but 64-bit on LP64 (this Linux build); the value is provably ≤ 0xFFFFFFFF (init 0xFFFFFFFF has zero high bits and every table entry is ≤ 32 bits, so `c` never exceeds 32 bits by induction), but callers rely on silent narrowing to store it in the 32-bit wire field: PngMagic.cpp:227 `int crc32c = crc.crc(...)` (well-defined modulo 2^32 in C++20, comparison at :228 works because both operands are signed 32-bit) and Frame.cpp:354/381/396/405 truncate into `toNet(uint32_t)`. Fix: declare `uint32_t crc(...)` and `uint32_t update_crc(uint32_t, ...)` so the 32-bit wire width is explicit in the type.
- L32: [error-handling] `int len` makes a negative length a silent no-op: `crc(buf, -1)` returns 0x00000000 (update loop skipped, 0xFFFFFFFF ^ 0xFFFFFFFF), which a caller would happily write to the wire as a bogus "valid" CRC; callers narrow `size_t` into it (Frame.cpp:396 `obl5size - 8` would go negative if an obl5 blob were < 8 bytes, PngMagic.cpp:227 `chunkSize + sizeof(chunkType)` is a size_t). Fix: take `size_t len` (matching zlib `crc32_z`) so a signed/unsigned slip becomes a compile warning instead of a wrong CRC.

### Low
- L39-42: [perf] `unsigned long crc_table[256]` is 2 KB per CCRC instance on LP64 (only 1 KB needed for `uint32_t`), stack-constructed per call (PngMagic.cpp:138 `parsePNG`, Frame.cpp:301 `toPng`, t_pngmagic.cpp:352), and the lazy flag forces a 256-entry table rebuild for every fresh instance. Fix: a `static constexpr uint32_t` table built at compile time (or delete the class per the shrink finding).
- L42: [shrink] `crc_table_computed` lazy-init machinery only pays off for streaming/multi-call reuse of one instance; the public API is single-shot `crc()`, so with a constexpr table the flag and the 0/1 bookkeeping (L28, L62, L78-79) exist only to save work that a compile-time table makes impossible. Fix: constexpr table, drop the flag.
- L32: [const] `unsigned char *buf` is non-const, forcing cast-away-const style casts at every call site (Frame.cpp:405 casts the string literal `(uint8_t *)"IEND"`, Frame.cpp:354 casts through `&ihdr`); reading through them is fine but the signature advertises mutation it never does. Fix: `const unsigned char *buf`.

## Notes
- CRC variant verified correct: table init `c = n`, 8 shifts against reflected polynomial 0xEDB88320 (L50-61), update `c = table[(c ^ byte) & 0xff] ^ (c >> 8)` (L82), init 0xFFFFFFFF, final XOR 0xFFFFFFFF (L34). This is CRC-32/ISO-HDLC (zlib/PNG/gzip CRC32); byte-for-byte identical to the reference appendix code reproduced at external/zlib/doc/rfc1952.txt:647-668. Test evidence: tests/t_pngmagic.cpp:266-282 rejects a single-bit IHDR CRC corruption with a "CRC" error, and :349-354 produces CRCs that PngMagic's parser accepts.
- Caller census (complete, whole-repo grep): `crc()` is called only at Frame.cpp:354/381/396/405 (PNG writer: IHDR, IDAT, obLT, IEND), PngMagic.cpp:227 (PNG chunk validator), t_pngmagic.cpp:354 (test fixture builder). No public entry point is dead; `update_crc`/`make_crc_table` are private with exactly one internal caller each. FrameSet save/load does not embed CCRC — FrameSet.cpp includes zlib but uses no CCRC.
- Wire format: PNG CRC fields are big-endian 32-bit; callers byte-swap via `CFrame::toNet` (Frame.cpp:284-296, a plain 4-byte reversal), so produced/consumed values match the 4-byte fields only on little-endian hosts (toNet is unconditional reversal, not a conditional htobe). The CCRC value itself fits 32 bits on both LLP64 and LP64, so the `unsigned long` return does not corrupt the wire on this LP64 target — "(needs verification ...)" only if a big-endian or LLP64 build is ever enabled; check `toNet` behavior there.
- UB/OOB check inside CRC.h: none found — `0xedb88320L` and `0xffffffffL` are representable as `unsigned long` under both models, all shifts are on unsigned types, table index is masked to 0..255, and loop bounds use the caller's `len` (a null `buf` with `len > 0` is caller UB, unverified by this header, as in zlib).
- ODR check: clean — all member functions are defined inside the class body (implicitly inline), there are no non-inline definitions, no static/global state, and `#pragma once` guards reinclusion. The 2 KB object is per-instance, not shared.
- Runtime verification suggestion: build and run `ctest --test-dir build -R pngmagic` to confirm the accept/reject CRC paths still pass, and optionally add a one-time `assert(crc((const unsigned char*)"123456789", 9) == 0xCBF43926)` (standard CRC-32 check value) if the header is kept rather than replaced by zlib `crc32`.
