# Audit: src/shared/DotArray.cpp
Date: 2026-11-17

## Summary
The `Dot` POD is live (it is `CFrame::draw`/`save`'s element type, Frame.h:184-185), but the entire `CDotArray` class has zero production instantiations in this repo — a whole-repo grep finds the only construction in `tests/t_dotarray.cpp`, and the class survives here only because `bin/utils/sync.sh:58` copies `DotArray.*` to the sibling editor project. Inside that mostly-dead class, both rasterizers are wrong in ways the current tests cannot see: `lineTab` iterates `dx+1` times regardless of which axis is dominant, so a steep line is truncated and a vertical line plots exactly one pixel (empirically reproduced), and `circle` plots only 4 of the 8 midpoint-algorithm symmetry points, leaving the left and right sides of every circle undrawn. Since this file is exported to another codebase, the algorithm bugs matter even though the runtime repo never calls them. Counts: 0 Critical, 3 High, 3 Medium, 3 Low.

## Findings

### High
**FIXED 2026-11-17 (BUG-H17):** dominant-axis bound + vertical-line test. **L86-100: [bug] `lineTab`'s loop `for (int i = 0; i <= dx; ++i)` runs `dx+1` times even when the line is steep (`dy > dx`), so the dominant-axis step never finishes: reproduced `(0,0)→(2,10)` plots only `(0,0)(0,1)(0,2)` — never reaches the endpoint — and a vertical `(5,0)→(5,10)` plots **1 dot**. Fix: iterate `for (int i = 0; i <= std::max(dx, dy); ++i)` (the Wikipedia general-Bresenham bound this otherwise faithfully copies); the existing test (t_dotarray.cpp:68) only exercises a horizontal line, which is why coverage misses it.
**FIXED 2026-11-17 (BUG-H17):** swapped-octant reflections + extrema test. **L124-130: [bug] `plot_sym` in `circle` plots only `(x0±dx, y0±dy)` — 4 points — omitting the four swapped-symmetry points `(x0±dy, y0±dx)` of the standard midpoint circle algorithm, so the octants adjacent to the horizontal axis are never drawn: reproduced with r=5 center (20,15), the circle has 20 dots and contains no point at `y==15` (the leftmost/rightmost extrema `(15,15)`/`(25,15)` are absent) — the "circle" is two C-shapes open left and right. Fix: add `add(color, x0+dy, y0+dx); add(color, x0-dy, y0+dx); add(color, x0+dy, y0-dx); add(color, x0-dy, y0-dx);`.
**TRIAGED 2026-11-17:** kept — file is rsync'd to the external LGCK editor (`bin/utils/sync.sh`) whose usage cannot be verified here. **DotArray.cpp:22-158 + DotArray.h:38-64: [dead] the whole `CDotArray` class has zero production callers in this repo: repo-wide grep (src/, tests/, examples/, itools/, android-project/) finds instantiation only in `tests/t_dotarray.cpp:25`; `Frame.h:27`'s `class CDotArray;` forward decl is unused (already flagged in Frame.cpp audit L28) and Frame.cpp only consumes the `Dot` struct via `std::vector<Dot>` (Frame.cpp:493/542). ~190 lines are kept alive by a coverage-tracked self-test and the editor-sync copy at `bin/utils/sync.sh:58` (needs verification — the editor checkout is not in this repo, so whether *it* calls `lineTab`/`circle` cannot be confirmed here). Fix: delete `CDotArray` and move the file to the editor repo (keeping the `Dot` struct, which Frame needs), or vendor the editor's copy.

### Medium
- L62-65: [ub][error-handling] `operator[](int i)` forwards a raw `int` to `std::vector::operator[]` — negative `i` converts to a huge `size_t` and `i >= size()` are both silent UB with no bounds check on a public API whose sibling methods deliberately clamp input (`add`, L41); the returned `const Dot&` is additionally invalidated by the next `add()`/`flush()`. Fix: take `size_t` (or keep `int` and range-check with LOGE + return a static empty `Dot`), matching the defensive style of `add`.
- L102, L119, L146 (header L49-50): [bug][shrink] `lineTab`/`circle` `return getSize()` narrows `size_t`→`int` (the declared return type should be `size_t`), and the value is the *total array size after optional clipping* — with `clear=false` it is cumulative across calls and with a `setLimit` active it silently under-counts clipped-away pixels, so callers cannot learn how many points the rasterizer actually generated. Fix: return the local generated count as `size_t` (or `void`) and document.
- L24-25, L43-47 (header L57, L61-64): [stdlib][shrink] `m_max`/`GROWBY` hand-rolls `std::vector`'s own geometric growth (reserve-1000-at-a-time guarded by `size() == m_max`) on top of a constructor that eagerly reserves 1000 `Dot`s (~12 KB) for every instance even one that adds a single dot. Fix: delete `m_max`/`GROWBY` and let `emplace_back` grow naturally, or offer a one-time `reserve(hint)`; the `size() == m_max` guard is also only correct because `flush()` (L52-55) clears without shrinking — a latent coupling.

### Low
- L30-32: [dead] empty user-declared destructor `~CDotArray()` adds nothing over the implicit one (the class holds only a `std::vector`); removing it from h:42 and cpp:30-32 costs one less non-trivial destructor.
- DotArray.h:26-31: [shrink] `Dot(int=0, int=0, uint32_t=0)` with all-default args creates implicit conversions from any three-argument `{int,int,uint}` context to `Dot`; no caller uses default construction (`t_dotarray.cpp` always passes coords) and the C-style `const int _x` args are discarded-copy idiom — make args non-defaulted/`explicit` (aggregate init `Dot{x,y,color}` used at DotArray.cpp:48 and Frame.cpp:553 already works without the ctor).
- L126-129: [perf] `plot_sym` emits exact duplicate dots when `dx == 0` (initial call `plot_sym(0, r)`, reproduced: `(20,20)` and `(20,10)` each stored twice) and again at `dx == dy`; harmless for painting but every consumer (`CFrame::draw`, pen restore) processes the duplicates. Fix: guard the mirrored pair on `dx != 0 && dx != dy` (moot once the 8-way fix above lands and dedup is done per octant pair).

## Notes
- Caller census (grep for `CDotArray`, `lineTab`, `circle`, `setLimit`, `dots()` across the whole repo): live in the runtime — only the `Dot` struct (Frame.h:184-185, Frame.cpp:493/542/553, exercised by t_frame.cpp:412-429); `CDotArray` and all its methods — `tests/t_dotarray.cpp` only. `android-project/app/jni/CMakeLists.txt:39` compiles DotArray.cpp into the Android target, so the dead class ships in the binary.
- Empirical repro (compiled DotArray.cpp with g++ -std=c++17): steep `lineTab` (0,0)→(2,10) → 3 dots ending (0,2); vertical (5,0)→(5,10) → 1 dot; `circle` r=5 → 20 dots, extrema (15,15)/(25,15) absent, duplicate top/bottom points. t_dotarray.cpp covers 94.9% line coverage (docs/compliance/src-coverage.md:18) yet asserts only endpoints/box-bounds, so all three algorithm defects are coverage-invisible.
- `circle` ignores `dot2.x` entirely (L113 uses `x0 = dot1.x`; L112 comment "Assume vertical for now" documents it): a horizontal-diameter input (`dy==0`) yields `r == 0` and silently plots one dot at `dot1.x` — intentional-by-comment, but the asymmetry is a trap for editor callers; consider `r = max(|dx|,|dy|)/2` with center from both endpoints.
- `add` clipping (L41) rejects negatives and `>= limit` (limit `-1` = unlimited sentinel); `setLimit(0, n)` therefore silently rejects every add — correct-by-construction but unlogged. Integer overflow in `abs(dot2.x - dot1.x)` (L79-80, L115) and `(dot1.y + dot2.y) / 2` (L114) requires |coords| near `INT_MAX`, unreachable from any UI-sized canvas — noted, not flagged.
- No serialization in this file — endianness not applicable. The `Dot` struct itself is not serialized anywhere; Frame's on-disk formats embed pixels, not dots.
- Suggested runtime verification: (1) add steep/vertical `lineTab` and full-octant `circle` assertions to `t_dotarray.cpp` against a reference Bresenham/midpoint implementation before fixing; (2) check the external editor repo's checkout for `lineTab`/`circle` call sites to decide delete-vs-fix priority for the dead-cluster finding; (3) `grep -r DotArray bin/utils/sync.sh` counterpart sync destination if maintained.
