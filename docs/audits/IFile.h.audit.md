# Audit: src/shared/IFile.h
Date: 2026-11-17

## Summary
IFile is a 22-line pure-virtual contract with zero documentation, and that silence is the root cause of every cross-backend divergence already catalogued in FileWrap.cpp.audit.md and FileMem.cpp.audit.md: the wire formats (string length prefixes, raw int passthrough), zero-size transfer semantics, close()/reopen side effects, and mode gating are each re-implemented independently by CFileWrap and CFileMem and each disagrees. The single most important defect is that every engine serializer takes `IFile&` and may receive either backend (FrameSet.cpp:216/400, gamemixin.cpp:1882/1921, map.cpp, actor.cpp, game.cpp, ISerial.h), so any unspecified behavior — e.g. `read(buf,0)` returning IFILE_NOT_OK only on disk — silently changes correctness when the backend changes. The header itself contains no UB and correctly declares a virtual destructor (L30); the problems are all underspecification and four production-dead members. Counts: 0 Critical, 3 High, 5 Medium, 3 Low.

## Findings

### High
**FIXED 2026-11-17 (BUG-H9):** wire format pinned in header. **L32-33, L37-38: [contract] no primitive/string wire format is specified anywhere in the header — string = 1/3/5-byte little-endian length prefix (FileWrap.cpp:182-216 vs FileMem.cpp:149-178), int = raw 4-byte host-order passthrough (FileWrap.cpp:61-69 vs FileMem.cpp:45-53) — so the format was implemented twice, privately, and the disk copy's decoder cannot read its own 32-bit string form (FileWrap.cpp:154-171, Critical in FileWrap.cpp.audit.md L10); because `CFrameSet::read/write(IFile&)` (FrameSet.cpp:216-217, 400-401) and every `read(IFile&)` serializer accept either backend, backend choice silently changes byte-level correctness. Fix: pin the encoding in a header comment and factor the length-prefix codec into one shared free function (or a non-virtual IFile helper on top of `read`/`write`) that both backends call, so the format exists exactly once.
**FIXED 2026-11-17 (BUG-H8/H9):** no-op semantics pinned + implemented. **L45-46: [contract][bug] zero-size `read`/`write` behavior is unspecified, producing a live divergence: CFileWrap returns IFILE_NOT_OK for `size==0` (`fread/fwrite(buf,0,1)` return 0, FileWrap.cpp:76, L84) while CFileMem returns IFILE_OK (FileMem.cpp:60-64, L72-79), so a savegame with an empty name false-fails only on the disk backend (gamemixin.cpp:1916/1936, per FileWrap.cpp.audit.md L13) and t_ifile.cpp:115-126 masks it by ignoring the `<<`/`+=` return values. Fix: state in the header that `read(buf,0)`/`write(buf,0)` are success no-ops and add the early `return IFILE_OK;` in CFileWrap.
**FIXED 2026-11-17 (BUG-H9):** flag-not-byte-count invariant documented. **L21-22, L45-46: [contract] `int read/write` actually return a `{IFILE_OK=1, IFILE_NOT_OK=0}` flag, but the `int` type and the two bare `#define`s carry no statement that byte counts are forbidden: every caller in the repo tests `!= IFILE_OK` or `!= 1` (map.h:47-57, recorder.cpp:100/151/209, Frame.cpp:103-105, maparch.cpp:186, t_ifile.cpp:195/391), so any future backend that returns bytes transferred — the conventional reading of `int read(void*, int)` — makes every successful multi-byte transfer fail those checks. Fix: change the return type to `bool` (no caller uses the int width) or document the invariant; while there, replace the two global macros with `enum`/`constexpr int` to keep the sentinels type-checked and out of the preprocessor namespace.

### Medium
- L48: [contract] **DOCUMENTED 2026-11-18** — header now pins close() as flush-and-release with the real divergences stated: CFileWrap returns false when nothing was open; CFileMem always returns true and destroys its buffer, so `getSize()`/`buffer()` must be inspected *before* close (the old header note claiming post-close inspection was "valid on CFileMem" was wrong and is corrected). Unifying CFileMem::close to non-destructive is a behavior change left as a maintainer call under the FROZEN-directive file. Original finding: close() semantics unspecified; backends diverged on return and side effects while real code consumes `buffer()`/`getSize()` before closing (`itools/mapzutil/src/main.cpp:252-259`, `t_ifile.cpp:493`).
- L44: [contract] **DOCUMENTED 2026-11-18** — header now pins: open() releases any previously held handle first (verified: `CFileWrap::open` calls `close()` first, closing the audit's record→playback leak path); legal mode vocabulary (must contain `r`, `w` or `a`; `"rb" "wb" "rw+" "ab"` in use); and the remaining divergence stated as a caller obligation — `'w'` truncates on disk but does **not** clear CFileMem's buffer, so generic code must not rely on truncation. Making CFileMem truncate on `'w'` is a behavior change left as a maintainer call under the FROZEN-directive file. Both backends already `std::string(...).c_str()` the views at the `fopen` boundary, so the NUL-termination worry is handled. Original finding: reopen/truncate/mode-vocabulary semantics unspecified; CFileWrap leaked the old FILE* on reopen; CFileMem 'w' didn't truncate (acknowledged TODO).
- L45-46: [contract] **DOCUMENTED 2026-11-18** — header now states the gate split as the contract: CFileMem rejects `read()` without `'r'` and `write()` without `'w'`/`'a'` as `IFILE_NOT_OK`; CFileWrap does not inspect the mode and defers to stdio, with both backends' null/closed-handle transfers returning `IFILE_NOT_OK` (the audit's null-`FILE*` crash no longer exists — `CFileWrap::read/write` early-return when `m_file` is null, verified). String operators bypassing the gates is pinned as a portability caveat. Tightening CFileWrap to the CFileMem gate is a behavior change left as a maintainer call under the FROZEN-directive file. Original finding: mode gating was implementation-specific; `read()` on a `"wb"` stream could be a clean failure, silent success, or segfault depending on backend.
- L50: [contract] **FIXED 2026-11-18** — both backends now reject negative `seek()` (`FileMem.cpp` early `return false`, disk via `fseek`), past-EOF seek succeeds on both, and the header pins exactly this. No caller in src/ or tests/ negative-seeks. Original finding: `seek()`'s bool was meaningful on disk but vacuous in memory (accepted any value, always true); past-EOF legality unspecified though `t_ifile.cpp` pins it must succeed on both.
**TRIAGED 2026-11-18:** interface contract FROZEN by maintainer — DO-NOT-TOUCH note added at top of `IFile.h`; the dead virtuals stay. - L40-41, L52-53: [dead][shrink] four of the 16 virtuals are production-dead yet impose implementation obligations on every backend: `operator>>(bool)` has zero callers repo-wide; `operator<<(bool)` is test-only (t_ifile.cpp:90); `flush()` is called only at t_ifile.cpp:340 (every other `flush()` hit resolves to `CDotArray::flush` or `CGame`); `mode()` has zero callers repo-wide (all `.mode()`/`->mode()` hits resolve to `CGame::mode()` — verified, consistent with FileMem.cpp.audit.md L25). Fix: delete `mode()` and `flush()` from the interface (keep `flush` as a CFileWrap-only concrete method if the recorder ever needs it) and drop the bool pair, or wire real users; each dead pure virtual is ~10 lines in each of two implementations plus every future backend.

### Low
- L32-53: [shrink] nothing in the interface is `const` — `mode()`, `tell()` and `getSize()` are observably read-only yet cannot be called through a `const IFile&` (no current caller holds one, so latent only); `mode()` also hands back a `std::string_view` into the implementation's `m_mode` member (FileWrap.cpp:252-255, FileMem.cpp:223-225) that dangles on the next `open()` — an undocumented ownership trap in a member that has no callers anyway (see dead finding above).
- L44: [shrink] the `mode = "rb"` default argument is used by zero call sites (all observed `open()` calls pass an explicit mode, per FileWrap.cpp.audit.md Notes L36), and CFileMem adds a further first-parameter default (`""`, FileMem.h:45) that is invisible through `IFile&` because default arguments are not inherited via the base — a signature that differs depending on the static type of the same object. Fix: delete both defaults.
- L40-41, L49-51: [ub][algo] contract-level gaps behind already-filed per-backend findings: the interface offers no byte-wide integer transfer, so both backends read a raw stream byte directly into a `bool` (FileWrap.cpp:220-221, FileMem.cpp:182-183 — non-canonical-bool UB, "fix once per backend" per those audits; the durable fix is a `uint8_t` operator or a documented 0/1 encoding here), and `long` offsets plus `int` transfer sizes (L45-46, L49-51) hard-cap the engine's file abstraction at 2 GiB on LLP64/Windows builds (same finding as FileWrap.cpp.audit.md L29 — the contract is the right place to fix the types).

## Notes
- Implementers: exactly two — `CFileWrap` (FileWrap.h:31) and `CFileMem` (FileMem.h:27); grep `public IFile` across the repo finds no other class, and tests instantiate only the concrete classes (no mock IFile exists). The virtual destructor (L30) is correctly declared; `ISerial.h` (src/shared) is the main consumer abstraction (`read/write(IFile&)`), and `CRecorder` (recorder.h:58) holds a non-owning `IFile*` — ownership of the file object always stays with the caller everywhere in the repo, so the interface's lack of any ownership contract is currently consistent (needs verification only against the external LGCK builder/editor that also compiles src/shared).
- Caller inventory used for the dead/usage verdicts: `>>(std::string)` + `<<(string)` production-live via OBL5 tags (FrameSet.cpp:400-401/216-217); `>>/<<(int)` live via OBL4 loader (FrameSet.cpp:1014-1054); `+=(string_view)`/`+=(const char*)` live via itools/mapzutil main.cpp:94-202 and t_ifile; `<<(const char*)` test-only (t_ifile.cpp:369) and a pure delegation in both backends (FileWrap.cpp:246-250, FileMem.cpp:217-221); `read`/`write`/`seek`/`tell`/`getSize`/`open`/`close` all have production callers through `IFile&`/`IFile*` (game.cpp, map.cpp, maparch.cpp, actor.cpp, animator.cpp, ai_path.cpp, gamestats.cpp, colormap.cpp, bossdata.cpp, layer.h, ISerial.h, recorder.cpp, helper.cpp, assetman.cpp, gamemixin.cpp). No caller ever assigns `read()`'s return to an int or uses it as a byte count — all 100+ sites compare against IFILE_OK/1, confirming the {0,1} convention is load-bearing but undocumented (High L45 finding).
- t_ifile.cpp is the effective executable spec of this contract: `infuse_create` (L44-135) and `test_ifile_serializer` (L334-452) run the *identical* op sequence against both backends and byte-compare the outputs (L505), i.e. the tests already assume the two backends are contract-identical — which the divergences above refute; the assumption survives CI only because `<<`/`+=`/`write` return values are ignored at L80-126 and the string round-trip never exercises a ≥65 535-byte string.
- The string encoding the two backends *did* agree to write (1 byte <0xff; `0xff`+2 bytes; `0xff`+`0xffff`+4 bytes, LE) is the de facto on-disk format for OBL5 tags; the FileWrap 32-bit decode branch (FileWrap.cpp:159-163) is dead, so the contract's fix should adopt the FileMem decode logic (FileMem.cpp:122-137, itself lacking payload bounds checks per FileMem.cpp.audit.md L10) as the single canonical codec.
- Suggested runtime verification: (1) same-`infuse_create`-style sequence through both backends asserting the IFILE_OK return of every call (not just tell()) — expect failures on CFileWrap at `write(buf,0)`/`<< ""`; (2) round-trip `<<`/`>>` of a 70 000-byte string through CFileWrap on a temp file — expect a corrupted string per FileWrap.cpp.audit.md L10; (3) `close()` a CFileMem then call `getSize()` — expect 0 (buffer destroyed) vs CFileWrap post-close behavior; (4) reopen an already-open CFileWrap twice and count fds with `ls /proc/self/fd` — expect one leak per reopen.
