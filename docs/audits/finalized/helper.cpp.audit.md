# Audit: src/shared/helper.cpp
Date: 2026-11-17

## Summary
helper.cpp is small and its zlib wrappers and `getUUID` are sound, but five of the eight declared functions (`toUpper`, `upperClean`, `copyFile`, `concat`, the raw-pointer `compressData`) have zero production callers — they exist only to be exercised by `tests/t_helper.cpp`, so most of the file is self-maintaining scaffolding. Inside that dead cluster, `copyFile`/`concat` ignore every `CFileWrap` read/write return value, so were they ever wired up, a short read or failed write would be reported as a successful byte-corrupted copy. The one production-reachable hazard is `readFile`'s size handling (`long` → `size_t` → `int` narrowing, unguarded `-1` from `getSize`). Counts: 0 Critical, 2 High, 4 Medium, 8 Low.

## Findings

### High
**FIXED 2026-11-17 (BUG-H15):** I/O results checked. **L86, L90, L127, L129: [error-handling] `sfile.read`/`tfile.write` return values ignored in `copyFile`/`concat` — `CFileWrap::read`/`write` return `IFILE_OK(1)`/`IFILE_NOT_OK(0)` (FileWrap.cpp L71-85), so a mid-stream read failure leaves the value-initialized zero-filled `buf` copied verbatim and a write failure (disk full) is invisible, yet the function returns `true` with an empty errMsg; today test-only (see dead-cluster finding) but these are the repo's intended copy utilities. Fix: check `!= IFILE_OK` and set errMsg + `result = false`, as `readFile` L206 already does.
**FIXED 2026-11-17 (BUG-H15):** size validated via `long`. **L204-206: [bug][error-handling] `readFile` (production-reachable: level.cpp:55/83/178): `size_t size = file.getSize()` turns `getSize`'s possible `-1` (ftell failure, unchecked per FileWrap audit L26) into SIZE_MAX → `std::vector<uint8_t> data(SIZE_MAX)` throws uncaught `std::length_error`; that `size_t` then narrows into `IFile::read`'s `const int size` (IFile.h L45), so any file > 2 GiB passes a negative count. Fix: take `long sz`, fail early on `sz < 0`, and guard `sz > INT_MAX` until IFile widens. (Needs verification that `ftell` can fail on an opened "rb" stream — a directory path opened via glibc `fopen` is the candidate repro.)

- Caller census (grep, whole repo incl. itools/packages/android-project/backup): live — `getUUID` (FrameSet.cpp:99), `compressData(vector<uint8_t>)` (Frame.cpp:121, 315; FrameSet.cpp:155), `compressData(vector<uint16_t>)` (layer.h:134), `readFile` (level.cpp:55, 83, 178; tests t_map.cpp:460, t_maparch.cpp:328/357). - IFile contract (IFile.h L21-22): `read`/`write` return `IFILE_OK`/`IFILE_NOT_OK`, never byte counts — `!= IFILE_OK` (the `readFile` L206 pattern) is the only valid success check; `t_helper.cpp`'s byte-identical round-trips (L64-136) cannot surface ignored-failure paths on a healthy disk.
- `compressData(vector<uint16_t>)` L188-189 compresses raw host-endian tile bytes, little-endian-only on disk — consistent with the engine-wide LE format noted in the FileWrap audit; intentional, not flagged.
- All three `compressData` overloads handle empty input correctly (`compressBound(0)` = 12, zlib accepts a null `data()` pointer with size 0); the L176/L191 shrink-resizes are correct. The raw overload's `new[]` at L157 requires caller `delete[]` even when `compress2` fails — ownership is documented only in a `t_helper.cpp:182` comment, another reason to delete it.
- `getUUID` output format, v4/RFC-4122 bit marking (L63/L65), and buffer sizing were verified correct (36 chars + NUL ≤ 40); tests already cover format + 100-sample uniqueness.
- Deleting the dead functions requires removing the matching blocks in `tests/t_helper.cpp` (registered via `tests/tmain.cpp`) per AGENTS.md dead-artifact conventions.
