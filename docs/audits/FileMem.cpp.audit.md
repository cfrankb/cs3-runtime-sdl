# Audit: src/shared/FileMem.cpp
Date: 2026-11-17

## Summary
CFileMem is the in-memory IFile backend that every untrusted asset byte stream passes through (`AssetMan::read → CFileMem::replace → CFrameSet::extract`, engine_hw.cpp:1176-1178, runtime.cpp:2963-2965), yet it validates nothing: `operator>>(std::string&)` memcpys an attacker-declared length (up to ~4 GiB) with no check against the remaining buffer, and `read`/`write`/`append` accept negative `int` sizes that become huge `size_t` memcpy counts (heap OOB read *and* write variants). There is no `size < 0` or `m_ptr > size` guard anywhere in the class, and `seek()` accepts any long unchecked, which then makes the `int leftBytes = m_buffer.size() - m_ptr` unsigned wrap in `read()` (L59) pass its bounds test and memcpy from a wild address. Everything else is small stuff: the append-mode open is off-by-one (unreachable), write-mode gating is inconsistently bypassed by the string writers, and several members/methods are dead. Counts: 2 Critical, 1 High, 3 Medium, 4 Low.

## Findings

### Critical
- L120-147: [bug][ub] **FIXED 2026-11-17** (docs/bugs/resolved/critical-triage-2026-11-17.md BUG-C1; `test_ifile_string_bounds`). Original finding: `operator>>(std::string&)` bounds-checks only the 1/2/4-byte length *prefix* (L122, L128), never the payload: L139 `str.resize(length)` + L142 `memcpy(str.data(), &m_buffer[m_ptr], length)` with `length` decoded straight from the stream (up to 0xffffffff) and no check that `m_ptr + length <= m_buffer.size()` → heap out-of-bounds *read* of up to ~4 GiB past a tiny asset buffer, then `return true` on garbage; this is the exact hole the FrameSet audit (FrameSet.cpp.audit.md High L396-408) deferred to "fix in FileMem too", reachable today from any crafted OBL5 tag stream via `engine_hw.cpp:1178 getFrame → extract → readSolid`. Bonus hole in the same function: the 32-bit extension at L133-137 reads 4 bytes but L128 only validated 2, so a 3-byte truncated tail (`0xff 0xff 0xff`) already reads 1-3 bytes past `m_buffer`. Fix: after decoding each prefix stage require `m_ptr + sizeof(field) <= m_buffer.size()`, and before resize/memcpy require `length <= m_buffer.size() - m_ptr`, returning false otherwise (decoding already leaves `m_ptr` untouched on the two existing early-outs — keep that).
- L35-43, L55-70, L72-79: [bug][ub] **FIXED 2026-11-17** (docs/bugs/resolved/critical-triage-2026-11-17.md BUG-C2; `test_ifile_negative_size`). Original finding: no negative-size validation on any transfer: `read(buf, -N)` passes `leftBytes >= size` (L60, signed) and L62 `memcpy(buf, ..., size)` converts the negative int to a huge size_t → guaranteed wild OOB read/crash (the exact sink the PngMagic audit L187-217 blames on `FileMem.cpp:60-64`); `write(buf, -N)`/`append(data, -N)` is worse — when `m_ptr >= N` the wrapped `newSize = m_ptr + size` (L37) is a *small* positive value ≤ `m_buffer.size()`, the L38 grow-check is skipped, and L41 `memcpy(m_buffer.data() + m_ptr, data, (size_t)-N)` becomes a heap out-of-bounds **write**; when `m_ptr < N` the wrap is huge and `resize` throws uncaught `std::length_error` → `std::terminate`. Note `operator<<(std::string_view)` L175 and `operator+=(const char*)` L198 narrow `size_t`→`int` implicitly, so any ≥2 GiB payload self-feeds this sink. Fix: `if (size < 0) return IFILE_NOT_OK;` at the top of `read` and `write` (and assert in `append`), and take `size_t` in `append`.

### High
**FIXED 2026-11-17 (BUG-H8):** negative seek rejected. **L109-113: [ub][error-handling] `seek(long)` is unchecked and always returns true: `m_ptr = p` converts a negative long to a near-2^64 size_t, after which the `int leftBytes = m_buffer.size() - m_ptr` (L59) unsigned-wraps to a value that *passes* the L60 test and L62 memcpys from `&m_buffer[huge]` (wild read/crash); a past-end positive seek enables the same, and a huge forward seek followed by any `write`/`append` turns L39 `resize` into an uncaught allocation throw. L59 also mis-signs for legitimate >INT_MAX (≈2 GiB) buffers, failing valid reads. Secondary callers rely on the return value (t_actor.cpp:150, t_boss.cpp:58) that can never be false. Fix: `if (p < 0 || (size_t)p > m_buffer.size()) return false;` (or clamp + report) and use size_t math at L59. (No in-repo caller passes a negative offset today — all observed seeks are literal 0 or non-negative parser positions; needs verification that crafted chunk-position math in PngMagic/FrameSet importers cannot produce a past-end seek before their own size gates fire.)

### Medium
- L85-86: [bug] append-mode positioning is off by one: `m_ptr = m_buffer.size() - 1` places the cursor on the *last existing byte*, so the next `append` overwrites it instead of extending (correct is `m_ptr = m_buffer.size()`). Currently unreachable — every observed `CFileMem::open` call uses `"rw+"`, `"wb"` or the default `"rb"` (t_ifile.cpp:282/476, t_boss.cpp:53, t_actor.cpp:144, t_animator.cpp:44, t_gamemixin.cpp:1351, mapzutil main.cpp:246; the `'a'` branch of the FileWrap registry is dead per FileWrap.cpp.audit.md L18) — but it is a live trap for the first `'a'` user. Fix: `m_ptr = m_buffer.size();`.
- L149-178 + L217-221 vs L72-79: [bug][error-handling] write-permission gating is inconsistent: `write()` (and therefore `operator<<int/bool` and both `operator+=`) enforce the `'w'`/`'a'` mode check, but `operator<<(std::string_view)` and `operator<<(const char*)` call `append()` directly and silently mutate the buffer of an object opened `"rb"` (and move `m_ptr`); `operator>>(std::string&)` likewise bypasses the `'r'` check that `read()` enforces. Masked today only because every writer happens to open `"wb"`/`"rw+"`. Fix: route both `<<`-string overloads through `write()` (one line each) so a single mode check governs all writes.
- L81-94: [error-handling] `open()` never clears the buffer for `'w'` modes (acknowledged `// TODO` at L90): reopening a reused instance leaves the old tail beyond the new writes, and `getSize()`/`buffer()` then report stale bytes (mapzutil main.cpp:252-259 `fwrite(buffer().data(), getSize(), ...)` and the t_ifile.cpp:493 disk-compare both consume exactly that). Unreachable today — every in-repo CFileMem is construct → replace/open → single open → use (verified by grep of all 57 CFileMem sites) — but the class invites the reuse. Fix: `if (m_mode.find('w') != npos) { m_buffer.clear(); }`.

### Low
- L180-183: [ub] `memset(&b,0,sizeof(b))` then `read(&b, 1)` stores one raw stream byte into a `bool`, so bytes 2..255 produce a non-canonical bool (UB per standard; benign on current compilers) — decode via `uint8_t` and `b = v != 0` (shared pattern with FileWrap.cpp:220, already noted there; fixed once per backend).
- FileMem.h:61 + L84: [dead][shrink] `m_filename` is assigned in `open()` and never read anywhere in the class — delete the member.
- L21-22, L30-33: [shrink] `#include <cstdio>` and `#include <cassert>` are unused in FileMem.cpp (no `assert`/stdio call in the file); the destructor's `close()` call is redundant (the vector members free themselves — `close()` only clears what destruction would clear anyway).
- L212-215, L223-225, L45 (FileMem.h): [dead] `mode()` has zero callers repo-wide (every `.mode()`/`->mode()` hit resolves to `CGame::GameMode`), `flush()` is exercised only by tests/t_ifile.cpp:340, and the `open()` default arguments (`""`, `"rb"`) are never used — all three exist only to satisfy the pure-virtual IFile contract / speculative convenience; keep the overrides but drop the defaults, or drop `mode()` from IFile if no consumer ever wants it (needs verification against the external LGCK builder/editor that also compiles src/shared).

## Notes
- IFile contract (IFile.h:21-22): `IFILE_OK=1`/`IFILE_NOT_OK=0`, so `return read(...)` in the bool operators (L47, L183) is correct-by-value, and `read` is all-or-nothing (no partial-read desync) — matches the PngMagic audit Notes L37 premise.
- Byte-order facts callers must know: the string length prefix is memcpy'd through the address of a `size_t` (L130, L135, L154, L165, L170) and `operator>>/<<int` is a raw 4-byte host-order passthrough (L45-53) — the entire encoding is little-endian-only, consistent with (and redundant to) the global LE note in FrameSet.cpp.audit.md Notes L43.
- Write/read dispatch symmetry verified: `<<` emits 1-byte for len<0xff, `0xff`+2-byte for <0xffff, `0xffff`+4-byte otherwise (L152-171), and `>>` decodes exactly that (L122-137) *modulo the missing payload bounds check* — unlike the FileWrap disk backend, whose 32-bit branch is dead (FileWrap.cpp.audit.md Critical); the two backends agree on zero-size strings (`<< ""`, `>> ""` both succeed here via the L140/L173 guards) where FileWrap's disk path false-fails.
- Mode strings actually used with CFileMem: `"rw+"` (t_boss/t_actor/t_animator/t_gamemixin/t_ifile round-trip tests), `"wb"` (t_ifile.cpp:476, mapzutil), default `"rb"` after ctor/`replace` (engine_hw, runtime, t_ifile extract tests). No `'a'` mode user exists — that finding is latent-only. The default-`"rb"` ctor is what lets `replace() → extract()` work without any `open()` call; `replace()` intentionally does not touch `m_mode`.
- `close()` (L96-102) *discards the whole buffer* — surprising semantics that would wipe a shared registry entry through the (dead) `CFileWrap::close → m_memFile->close()` path; already flagged as a sibling fact in FileWrap.cpp.audit.md Notes L34, harmless for all current direct users (close after done).
- Edge-case trivia, not filed: `&m_buffer[m_ptr]` at `m_ptr == m_buffer.size()` with `size == 0` (L62) is a technically-UB `vector::operator[]` end-index reference; `getSize()` `size_t→long` (L106) and `tell()` `size_t→long` (L117) narrow only on >8 EiB/absurd streams.
- Suggested runtime verification (ASan): (1) `replace()` 3 bytes `{0xff,0xff,0xff}` then `>> str` — expect heap-buffer-overflow at L135 today, clean false after prefix-bounds fix; (2) `replace()` `0xff + 0x00100000` length into a 100-byte buffer — expect ~1 MiB wild read at L142; (3) `mem.open("x","rw+"); mem.write(buf,-4)` with ≥4 bytes written first — expect heap OOB write at L41; (4) `mem.seek(-1)` then `read(buf,4)` — expect wild read at L62; all four must return failure cleanly after fixes. (5) `open("f","ab")` on a 5-byte buffer, write 1 byte, `getSize()` — today stays 5 (byte clobbered), after fix should be 6.
