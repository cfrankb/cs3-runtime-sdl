# Audit: src/shared/PngMagic.cpp
Date: 2026-11-17
Correction (2026-11-17): FileWrap audit found the static memory-file registry (`addFile`/`findFile` path) has zero callers repo-wide — the "live findFile path" premise in this report is wrong. The parsePNG entry points via `FrameSet.cpp:695` and `tileset_tex.cpp:59/102` remain live.

## Summary
`parsePNG` trusts every attacker-controlled chunk length: the per-chunk CRC check (which any attacker can satisfy for arbitrary bytes) is the *only* gate before the chunk payload is memcpy'd, so IHDR/PLTE/tRNS payloads of any declared size are copied verbatim into fixed stack buffers and obLT `Count` drives unbounded `resize`/`memcpy` reads past the chunk — multiple confirmed stack and heap out-of-bounds writes/reads on the live asset path (`FrameSet.cpp:695` dispatch and `tileset_tex.cpp:59/102`, neither wrapped in try/catch). Secondary cluster: the 4-byte chunk-length field and the `CFrame` 4096-dimension cap are never sanity-checked, so 4 bytes of attacker input also produce uncaught `length_error`/`invalid_argument` → `std::terminate`. The row-decode math itself (filter reconstruction, fData indexing, uncompress sizing) is verified in-bounds once dimensions are capped. Counts: 2 Critical, 2 High, 4 Medium, 9 Low.

## Findings

### Critical
- L236, L252, L272: [bug][ub] **FIXED 2026-11-17** (docs/bugs/resolved/critical-triage-2026-11-17.md BUG-C3; verified in code 2026-11-18: `chunkSize != 13` rejects IHDR, `chunkSize > sizeof(plte) || chunkSize % RGB_BYTES` rejects PLTE, `chunkSize > sizeof(trns)` rejects tRNS — all before the `memcpy`). Original finding: attacker-sized chunk payload copied into fixed stack buffers with no length check — `memcpy((uint8_t*)&ihdr + 8, chunkData, chunkSize)` into a 24-byte `png_IHDR` (16 bytes of room, IHDR content is 13), `memcpy(plte, chunkData, chunkSize)` into `uint8_t plte[256][3]` (768 B), `memcpy(trns, chunkData, chunkSize)` into `uint8_t trns[256]`; the L227-232 CRC check passes trivially because the attacker computes the CRC over the oversized payload, so any crafted PNG (tileset load, engine `getFrame → extract → parsePNG`) smashes the parse loop's stack with up to 2 GiB of fully controlled bytes.
- L291-296, L302-304: [bug][ub] **FIXED 2026-11-17** (BUG-C3; verified in code 2026-11-18: both the OBLT_VERSION0 path (`needed = 12 + 2*sizeof(uint16)*Count`) and the OBLT_VERSION2 path (`needed = 12 + sizeof(oblv2DataUnit_t)*Count`) reject `needed > chunkSize` in unsigned math before `resize`/`memcpy`). Original finding: obLT `Count` is a raw attacker uint32 (no toNet, no bound against chunk size): `obl5t_sx.resize(Count)` + `memcpy(..., chunkData + 12, 2*Count)` (and `sy` at `+12+2*Count`) / `memcpy(obl5t_metadatav2.data(), chunkData + 12, 16*Count)` read far past the `chunkSize+4`-byte heap chunk buffer, leaking adjacent heap memory into frame metadata that `explode()` then turns into frames; a big `Count` instead throws uncaught `length_error`/`bad_alloc` from `resize`.

### High
**FIXED 2026-11-17 (BUG-H4):** MAX_FRAME_DIM gate before allocation. **L338: [error-handling] `std::make_unique<CFrame>(width, height)` uses raw IHDR dimensions (rounded up to /8) but the ctor throws `std::invalid_argument` for dims <0, >4096 (Frame.cpp:43-47) — any PNG wider/taller than 4096 px, or with a >INT32_MAX dimension that wraps negative, terminates the runtime: no caller of `parsePNG` catches (grep: only catches in src are layerdata.cpp:60, main.cpp:254, colormap.cpp:41; tileset_tex.cpp:59/102 and the FrameSet.cpp:695 path have none). Fix: after `toNet`, clamp-check `width <= 4090 && height <= 4096` (post /8-round values ≤ 4096) and return `set.setLastError("png too large")` cleanly.
**FIXED 2026-11-17 (BUG-C3):** chunk lengths range-checked. **L187-217: [bug][ub] the 4-byte chunk length is never range-checked before use: `chunkSize` ≥ 0x80000000 becomes a negative int32 after `toNet` (L193), so `std::vector<uint8_t> chunkDataRaw(chunkSize + sizeof(chunkType))` (L210) sign-extends — `chunkSize = -huge` → uncaught `length_error`/`bad_alloc` abort, `chunkSize ∈ {-1,-2,-3}` → wraps to a 1-3 byte vector, and `file.read(buf, negative)` on a CFileMem-backed asset (the live container path via `CFileWrap::open → findFile`) passes a negative int straight into `memcpy` as `size_t(huge)` (FileMem.cpp:60-64) → guaranteed crash; positive sizes also let a 12-byte file demand a ≤2 GiB allocation before the read (L211) fails. Fix: after L193, `if (chunkSize < 0 || (long)chunkSize + 12 > fileSize - (pos - 8)) { setLastError; return false; }` — one check kills the negative, wrap, and allocation-amplification variants.

### Medium
- L169 + L587, L673: [ub][error-handling] **FIXED 2026-11-18** (`memset(plte, 0, sizeof(plte))` added next to the `trns` init; pinned by `test_png_iend_idat_plte` no-PLTE case → deterministic black palette). The size-vs-bit-depth half was *declined*: `plte[line[x]]`/`trns[line[x]]` are in-bounds for every index (≤ 255 vs 256-entry arrays), so the memset fully removes the UB, while mandating a full `2 << (BitDepth-1)` palette would reject spec-legal short PLTEs for zero memory-safety gain — missing entries now read as black. Original finding: `plte` was the only palette buffer *not* zero-initialized (contrast `trns` at L171), and neither its presence nor its size is validated against the bit depth: a palette PNG with no PLTE, or a PLTE shorter than the indices used in IDAT, makes `memcpy(&rgba, plte[line[x]], 3)` read indeterminate stack bytes into pixel colors (UB, nondeterministic output) instead of failing.
- L431-443, L639-651: [error-handling] **FIXED 2026-11-18** (both `_8bpp` and `_4bpp` sites capture `expectedSize` before `uncompress` and reject `dataSize != expectedSize` with `lastError "truncated IDAT stream"`; pinned by `test_png_iend_idat_plte` short-stream case). Original finding: `uncompress` returning `Z_OK` was accepted without comparing the returned `dataSize` to the expected `pitch * height` — a crafted zlib stream that decompresses to fewer bytes left the tail of `fData` zero-filled (filter byte 0), silently producing black/transparent rows instead of an error; the sibling decoders explicitly require `destLen == expected` (Frame.cpp:207; FrameSet readSolid already flagged for the same gap).
- L283-286: [ub] **FIXED 2026-11-17** (BUG-C3; verified in code 2026-11-18: `if (chunkSize < 12) { setLastError("obLT chunk too small"); return false; }` now precedes `memcpy(t + 8, chunkData, 12)`). Original finding: the obLT field header is copied with `memcpy(t + 8, chunkData, 12)` before `chunkSize` is checked, so an obLT chunk with length < 12 (valid CRC) reads past the small heap chunk buffer, and the resulting garbage `Version`/`Count` feed the L291-304 memcpy storm above.
- L184, L276-279: [error-handling] **FIXED 2026-11-18** (`if (iend_found) break;` at end of loop body; round-trip safe — the writer emits obLT *before* IEND, Frame.cpp:320 vs 333; pinned by `test_png_iend_idat_plte` trailing-garbage and post-IEND-obLT-ignored cases). The optional LOGW of trailing byte count was skipped (YAGNI — silently tolerated padding is the spec behavior). Original finding: the loop never broke on IEND — any trailing byte after IEND (email/PNG-bundle padding is common) made the next iteration fail at L188-192 and rejected an otherwise-valid image, while chunks *after* IEND (including a second obLT at L281-310, whose metadata then overrode the real one) were processed as if legitimate.

## Notes
- Verified in-bounds once dimensions are capped: with dims ≤ 4096 (enforced only by the L338 ctor throw, see High), `_8bpp` `pitch*height ≤ 16385×4096` and every `fData[pitch*y + 1 + x*pw]`, filter-source (`prLine`, `line[x-1]`) and `rgb[(offsetY+y)*frame->width()+x]` index stays within the buffers; `_4bpp` likewise with `pitch ≤ 2049`. `uncompress` rejects oversized streams (Z_DATA_ERROR), so `fData` can never be overflowed — the residual gap is under-run zero-padding only (Medium above).
- The chunk CRC (L227-232) is computed over type+data per the PNG spec and runs *before* every chunk handler, but provides zero protection against the Critical findings since the CRC is recomputed from the attacker's own oversized payload; only the tEXt-class "ignored chunk" path is inert.
- Both `IFile` impls are all-or-nothing on reads (FileWrap.cpp:71-77 `fread(...,1)`; FileMem.cpp:55-70), so the manually-tracked `pos` never desyncs from the stream on success paths; FileMem's negative-size handling (int→size_t in `memcpy`) is cross-covered by the FileWrap/FileMem audit — the fix *here* is the chunkSize gate, not FileMem.
- obLT `Version`/`Count`/`sx`/`sy` are read in *native* byte order with no `toNet` (L285-304), matching `CFrame::toPng`'s writer and the test builder comment "written by toPng in native byte order" (t_pngmagic.cpp:406) — LE-only custom chunk, round-trips in-repo (same fact as FrameSet audit Notes L44); a BE-written PNG of 1025×1 silently loses its obLT instead of failing.
- `explode()` call sites L363/L367 pass raw file-controlled `count`/`sx`/`sy`/v2-units with no validation — the *validation gap inside explode* is reported in Frame.cpp.audit.md (High, L923-961); the parse-side OOB read (Critical above) is this file's share. `skipOblt=true` callers (tileset_tex.cpp:59, :102) bypass explode entirely; the engine `getFrame → FrameSet::read → parsePNG` path does not.
- Correctly rejected (positive checks, pinned by tests/t_pngmagic.cpp): interlaced, BitDepth ∉ {4,8}, grayscale/grayscale-alpha (test_png_4bpp "unsupported png"), bad filter bytes, corrupt zlib with valid chunk CRC, split-IDAT concatenation decodes identically, orgPos dispatch; `png_chunk_OBL5 = "obLT"` matches the writer (Frame.cpp:992-995).
- Suggested runtime verification (all under ASan, expected outcome after fixes = clean `false` + non-empty lastError): (1) IHDR chunk declared length 40 / PLTE length 4096 / tRNS length 1024 with recomputed CRCs; (2) obLT v0 chunk `chunkSize=12, Count=1000` and a `chunkSize=4` obLT; (3) 5000×8 RGBA PNG (expect clean "too large", today: uncaught `invalid_argument`); (4) chunk length field 0xFFFFFFFF and 0xFFFFFFFE in a disk-backed *and* a CFileMem-backed (container) stream; (5) 8 junk bytes appended after IEND (must still parse); (6) palette PNG with PLTE omitted and with 3-byte PLTE (deterministic colors after memset fix).
