# Audit: src/shared/FrameSet.cpp
Date: 2026-11-17

## Summary
CFrameSet is the frame-set container plus importers for five legacy formats (IMA, IMC1, GE96, OBL3/4/5) and the OBL5 serializer; overall structure is sound (IFile return codes are mostly checked, tmp-frame vectors use unique_ptr so import failure paths are leak-free), but the IMC1 RLE decoder writes unbounded runs into a fixed heap buffer and is triggerable by any crafted asset fed through `extract()` (e.g. `engine_hw.cpp:1171-1189`, `runtime.cpp:2959`). Secondary high-severity issues: unvalidated tag-stream parsing that leans on FileMem's unchecked string resize, a write/read dimension-cap mismatch that makes IMA-imported sets unre-savable, unchecked `toSubset` bounds with a size_t underflow crash, and a header-declared DoS-uncapped 1 GiB decompression pre-allocation. Counts: 1 Critical, 4 High, 9 Medium, 10 Low.

## Findings

### Critical
- L829-848: [ub][bug] **FIXED 2026-11-17** (docs/bugs/resolved/critical-triage-2026-11-17.md BUG-C4; `test_frameset_hostile_imc1`). Original finding: importIMC1 RLE decoder trusts a crafted 0xff escape: a 0xff at `imc1[SizeData-2]` reads `ptrIMC1[2..3]` 2 bytes past the end of the `imc1` vector (L834), and the run length `ptrIMC1[2] + ptrIMC1[3]*256` (up to 65535) is written at `*ptr` with no bound against `destSize` (L834-837) — a 1x1 IMC1 declares destSize=64, so a crafted file overflows the `dest` vector by up to ~64 KiB; the post-loop `cpt > SizeData` check (L849) fires only *after* the out-of-bounds writes. Fix: track remaining source bytes (`SizeData - cpt`) before dereferencing the 4-byte escape, and clamp/verify each run against `destSize - (ptr - dest.data())`, failing the import when exceeded.

### High
**FIXED 2026-11-17 (BUG-H5):** `file >>` results checked. **L396-408: [error-handling][ub] readSolid ignores the `file >> key` / `file >> val` return values (L400-401) and `CFileMem::operator>>(std::string)` (FileMem.cpp:139-144) resizes and memcpys an unvalidated 1/3/5-byte length prefix with no check that `m_ptr + length <= m_buffer.size()` — a crafted OBL5 tag stream (tagCount ≤ 100 passes L389) triggers a heap out-of-bounds *read* of up to 4 GiB inside FileMem on the live asset path (`engine_hw.cpp:1178 getFrame -> extract -> readSolid`). Fix: check each `file >>` result, and bound the declared string length against remaining stream bytes before resize (fix in FileMem too, where any tag-reading caller inherits it).
**FIXED 2026-11-17 (BUG-H5):** writer capped at MAX_IMAGE_SIZE. **L128 vs L326: [bug] writeSolid accepts frame dimensions ≤ 4096 while readSolid rejects anything > MAX_IMAGE_SIZE=512, and importIMA/importIMC1 happily create frames up to 2040x2040 (`len * FNT_SIZE`, L744, L866) — such a set saves cleanly as OBL5_SOLID but the identical file is rejected on load (`Invalid frame dimensions`), an unrecoverable round-trip loss; OBL5_UNPACKED likewise can't write them (CFrame::write caps at MAX_IMAGE_SIZE, Frame.cpp:94). Fix: use MAX_IMAGE_SIZE in the writeSolid validator (L128) so the writer refuses what the reader cannot accept.
**FIXED 2026-11-17 (BUG-H5):** range clamped in int math. **L1356-1366: [bug] toSubset has zero input validation: `end == -1 ? getSize() - 1 : end` (L1358) computes `size_t 0 - 1` on an empty set, and `dest.reserve(last - start)` (L1359 -> L1370) then calls `vector::reserve` with a huge size_t -> uncaught `std::length_error`/`bad_alloc` crash; out-of-range `start`/`end` index `m_frames[i]` (L1363) directly (OOB read). Fix: clamp `start`/`end` to `[0, size-1]` in int arithmetic and early-return when the range is empty. (Only test callers today, tests/t_frameset.cpp:428, but this is the shared public API.)
**FIXED 2026-11-17 (BUG-H5):** totalSize bounded by srcSize*1032+1024. **L335-348: [perf][algo] readSolid pre-allocates `buffer(totalSize)` (L344) purely from declared dimensions: 1024 frames x 512x512x4 = 1 GiB allocated from a ~4 KiB file, since the L304 file-size check only validates the *compressed* blob size; uncompress fails afterward but the allocation spike (plus `srcBuffer` + per-frame copies) is the DoS. Fix: cap totalSize against a fraction of file size (e.g. `srcSize * 300 + slack` style bound, or zlib's compressBound reverse) before allocating.

### Medium
**FIXED 2026-11-18 (maintainer-approved, option 1): declared deep-copying
`CFrameSet(const CFrameSet &)` and `operator=(const CFrameSet &)`; the
compiler-generated shallow forms are now suppressed. Source-compatible — all
previously-compiling copy sites keep compiling but now duplicate frames
instead of risking double-free. Pinned in `tests/t_frameset.cpp` (copy-ctor
independence, self-assignment).**
- FrameSet.h:51 / cpp:532: [bug] rule-of-three violation: the only declared copy-assignment takes a *non-const* ref, so the compiler still declares the implicit `operator=(const CFrameSet&)` and the implicit copy constructor, both shallow-copying the owned raw `m_frames` pointers -> latent double-free for any value-copy site (none found in-repo — needs verification for external builder/editor users). Fix: `delete` the implicit forms or implement proper const-ref copy semantics.
**FIXED 2026-11-18 (BUG-H18):** `int m_currFrame = -1;`. - FrameSet.h:85 / cpp:75-79: [ub] `m_currFrame` is never initialized in the default constructor or the pointer ctor (L81-95); `currFrame()` (L1378) returns an indeterminate value if read before `setCurrFrame`. No in-repo caller reads it (only tests/t_frameset.cpp, always after set — needs verification of builder users).
**FIXED 2026-11-18 (manual leak review): local `delete` on the parse-failure return; frame never escapes the method so the ownership contract is untouched.**
- L474-479: [leak] read()'s OBL5_UNPACKED branch `new CFrame`s per frame but on `frame->read` failure returns without deleting or adopting the frame — one CFrame leaked per failed parse. Fix: use a `unique_ptr` local and release only on success (readSolid at L381-383 already does this right).
- L352-367: [error-handling] readSolid accepts `uncompress` Z_OK even when `destLen < totalSize` — a truncated zlib stream silently yields zero-padded frames (buffer is value-initialized) instead of an error; the sibling CFrame::read explicitly requires `destLen == expected` (Frame.cpp:207). Fix: compare destLen to totalSize and fail on mismatch.
- L1197-1203 (recomputed L1228-1230): [integer] importOBL3 computes `oblHead.iLen * OBL3_GRANULAR` as uint32 math before converting to int: `iLen = 2^28 + k` (k ≤ 32) wraps to `16k ≤ 512` and sails through the dimension gate, so a malformed header is accepted and parsed as garbage frames (no OOB, but silent bad data). Fix: validate `iLen`/`iHei` in uint32 against `MAX_IMAGE_SIZE / OBL3_GRANULAR` before multiplying.
- L1028-1034: [error-handling][ub] importOBL4 ignores the bool results of `file >> mode / len / hei` — on a truncated stream `mode`, `len`, `hei` stay uninitialized and the dimension check at L1037 reads indeterminate ints (UB). Fix: check each `>>` result. (Same pattern, lower impact, at L1014 `file >> size`.)
- L348-349: [error-handling] readSolid ignores the return value of `file.read(srcBuffer.data(), srcSize)` before uncompressing; also passes `long srcSize` into `IFile::read(void*, int)` — narrowing that misreads sizes > INT_MAX on huge streams (same long->int at L711 importIMA). Fix: check IFILE_OK; the L304 bounds check already keeps srcSize < fileSize.
- L200-211 vs L389: [bug] writeSolid writes an uncapped `tagCount` while readSolid hard-rejects `tagCount > 100` — a set with >100 tags (reachable via repeated `setTag`) produces a file the reader refuses; relatedly, OBL5_UNPACKED silently persists no tags at all (L256-268), so a UUID-less set gets a *new* UUID on every load (L502-506). Fix: cap/validate tag count on write to match the read limit.
**FIXED 2026-11-18 (maintainer ruling on leak review): the set retains slot
ownership, so `set()` now deletes the replaced frame (self-overwrite guarded)
and `resize()` truncation deletes the dropped tail. `resize()` growth still
inserts null slots — fill before dereference. Pinned in
`tests/t_frameset.cpp`.**
- L1373 / L1398-1402: [leak][bug] `set(i, frame)` overwrites an owned slot without deleting the old frame (caller-ownership is documented only in tests/t_frameset.cpp:387) and `resize()` grows with nullptr slots while leaking the truncated tail (its own `// TODO: fix memory leaks`); null slots then crash direct dereferencers such as `gamemixin.cpp:969 *(*frames)[num]` and write paths using `m_frames[i]->...` (L120/L260). Fix: delete-on-replace (or take unique_ptr), and fill resize-growth with real frames or reject.

## Notes
- Verified OBL5 byte symmetry: `write()` = sig(4)+count(4)+format(4); SOLID = compressedSize(4) + per-frame w/h(2+2) + blob + tagCount(4) + TLV tags, exactly mirroring readSolid (L293-408); UNPACKED delegates to CFrame::write/read (2+2+4+4+n, Frame.cpp:89-214) symmetrically.
- All OBL/GE96/IMC1 serialization is native-endian with native struct packing (L171, L184-185, L242, L296 write 4-byte slices of `size_t`/`long`/`uLong`/`int` variables; USER_MCXHEADER/USER_OBL3HEADER at L886-904/L1129-1170 have no `#pragma pack`). Fine for the current LE-only targets (x86/arm/wasm32); would silently corrupt on a big-endian port.
- The `oBL5` PNG chunk written by toPng (L1323-1333) stores Version/Count/sx/sy in native order and only Length in `toNet` — this matches the parser in PngMagic.cpp:281-297, so it round-trips in-repo but is not a portable custom chunk; CFrame::toPng then overwrites Length identically (Frame.cpp:394-395).
- `bitmap2rgb` always maps through the hard-coded `g_original_palette` (L35-67) with index offset -16 for OBL3/OBL4/GE96 and 0 for IMA/IMC1; the GE96 header's embedded 256-color palette (L902) is read into the struct and ignored, and GE96 records' PtrPrev/PtrNext linked-list fields are ignored in favor of sequential layout (L949-955) — consistent with legacy LGCK assets, but (needs verification against real .mct/.obl sample files before trusting third-party assets with custom palettes).
- Runtime untrusted-input path: `engine_hw.cpp:1171-1189` (`getFrame`) and `runtime.cpp:2959-2965` (`loadAppIcon`) hand arbitrary asset bytes to `extract()`, so all importOBL*/IMC1/IMA bounds findings are remotely-reachable via shipped/replacement asset files; callers of `removeAt(0)` guard with a size check (verified at engine_hw.cpp:1182, tileset_tex.cpp:66-69).
- FrameSet.cpp uses `INT_MAX` (L134, L163, L336) without including `<climits>`; it compiles via transitive includes today — fragile.
- CFileWrap's file-backed `operator>>(std::string)` has an unreachable 0xffff 32-bit branch (FileWrap.cpp:157-171) and reads its length byte into an int LSB (LE-dependent); unreachable in practice only because TAG_VAL_MAX=1024 keeps FrameSet tags below the 16-bit escape.
- Suggested runtime verification: add negative tests to tests/t_frameset.cpp — (1) synthetic IMC1 with a 0xff escape whose run exceeds `len*hei*64` (must fail cleanly under ASan), (2) OBL5 with a truncated tag stream and with `tagCount=101`, (3) save/load round-trip of a 600x600 frame to pin the writer cap, (4) `toSubset(sub, 0, -1)` on an empty set (must not throw length_error).
