# Audit: src/shared/Frame.cpp
Date: 2026-11-17

## Summary
CFrame's own serialization and PNG/BMP emitters are byte-accurate (toPng size math verified exact against bytes written; read/write OBL5 0x500 layout verified symmetric and its bounds/decompression checks are stricter than readSolid's), but the class is an exception-based island in a bool/lastError codebase and nothing on the live asset path catches those exceptions: `explode()` feeds completely unvalidated file-supplied obLT metadata into `clip()`/the dimension-throwing constructor, so a crafted PNG loaded through `parsePNG` (FrameSet.cpp:695 signature dispatch, reached from `engine_hw.cpp` getFrame per the FrameSet audit; the only catches in src are layerdata.cpp:60, main.cpp:254, colormap.cpp:41 — none on this path) terminates the runtime. The second confirmed live bug is `toPng()` returning **true** after a compression failure with the png buffer cleared, which callers at runtime.cpp:1783 and FrameSet.cpp:1336 ignore, silently writing empty "screenshots"/exports. Beyond that the file carries a large test-only editor API and four inline line-drawers with zero callers anywhere, plus several latent OOB/throw footguns around the unprotected `m_rgb.size() == m_width*m_height` invariant. Counts: 0 Critical, 2 High, 9 Medium, 12 Low.

## Findings

### High
**FIXED 2026-11-17 (BUG-H4):** both overloads pre-validate and fail soft. **L923-937, L940-961 (+clip L652-687, ctor L43-47): [error-handling][bug] neither `explode` overload validates file-controlled obLT data (count, sx/sy, x/y) against `m_width`/`m_height` or against the 4096 ctor cap — `clip(mx,0,sx[i],sy[i])` L933 / `clip(unit.x,unit.y,unit.sx,unit.sy)` L953 throw `std::out_of_range` from `at()` (L681) when cumulative `mx`/`x` exceeds the frame, or `std::invalid_argument` when any sx/sy > 4096; both overload sites are called with raw PNG chunk fields at PngMagic.cpp:363/367, reached on the untrusted asset path with no try/catch in src → uncaught exception → `std::terminate`. Fix: in explode, pre-validate `sum(sx) <= m_width`, `sy[i] <= m_height`, `unit.x+unit.sx <= m_width`, `unit.y+unit.sy <= m_height` and dims ≤ 4096, setting `m_lastError` and returning the partial/empty set instead of throwing (same pre-flight for `split`).
**FIXED 2026-11-17 (BUG-H4):** returns false; FrameSet propagates. **L316-321: [error-handling][bug] `toPng` sets `m_lastError` on `compressData` failure but **returns true** with `png` already cleared (L300), and the message says "decompression" on a compression error (L318); both live callers ignore or trust it — runtime.cpp:1783 (`takeScreenshot`) writes the empty vector to `screenshot*.png` unconditionally, FrameSet.cpp:1336 discards the bool and returns success. Fix: `return false`; fix the wording; check the result at runtime.cpp:1783.

### Medium
- Frame.h:62-64 + L435, L451, L866, L967, L983, L999: [bug][shrink] the `m_rgb.size() == m_width*m_height` invariant is unenforced: `setRGB()` (Frame.h:64) swaps in a vector without touching dimensions and `getRGB()` hands out a mutable reference (used as a write target at runtime.cpp:1775 and PngMagic.cpp:339), while `setTransparency`/`hasTransparency`/`isEmpty`/`abgr2argb`/`argb2arbg`/`fill` loop `i < m_width*m_height` with unchecked `m_rgb[i]` → heap OOB read/write on any desynced frame (no in-repo caller desyncs today — verified tests/t_gamemixin.cpp:239/362 pre-size correctly; needs verification for builder users); `write()` (L117-118) then serializes `m_rgb.size()*4` bytes against a w/h header, producing archives its own `read()` rejects at the L207 destLen check. Fix: in `setRGB` reject/resize to `w*h`; iterate `m_rgb.size()` in the flat loops.
- L103-115: [error-handling] `write()` emits the w/h/filler header before the zero-size check (L111), so a 0×N frame commits a partial OBL5 record into the shared stream (CFileMem has no rollback) that desynchronizes the rest of an OBL5_UNPACKED archive being written by FrameSet.cpp:260; move the empty-frame check ahead of the header writes.
- L178-199: [integer] `compressedSize` (raw uint32 from file) is bounds-checked as `(long)` (L186) but on 32-bit targets (wasm32/armv7 builds) `long` is 32-bit: values ≥ 2^31 go negative, trivially pass the tell+size check, then `vector<uint8_t> cData(compressedSize)` (L198) attempts a ~4 GiB allocation (uncaught `bad_alloc` → crash) and `file.read(..., compressedSize)` narrows to a negative `int` size (IFile.h:45); needs verification whether >2 GiB container files ever occur in the wild. Fix: reject `compressedSize > UINT32_MAX/2` (or `> fileSize` as unsigned) before allocating.
- L820, L841: [bug] `shiftLEFT`/`shiftRIGHT` guard on `m_height <= 1` instead of `m_width <= 1` (copy-paste from shiftUP/shiftDOWN): a valid 1-row × N frame is silently refused (bogus `m_lastError`, no shift) by the one live caller `gamemixin.cpp:505 bitmap.shiftLEFT(false)`. Fix: guard `m_width <= 1` (keep the `m_width <= 0` emptiness check).
- L906: [bug] `shadow(factor)` computes `/ factor` with zero validation — `shadow(0)` is integer division by zero (SIGFPE); factor is public int, no caller clamps. Fix: `if (factor <= 0) return;` + `m_lastError`.
- L564-650: [algo][perf] `floodFill`/`floodFillAlpha` are recursive scan-fill: when `bOldColor == bNewColor` the repaint is a no-op so the up/down neighbor checks (L575-583, L595-603) recurse mutually forever → guaranteed stack-overflow crash; even with old != new, maze-shaped regions drive recursion depth proportional to region size (up to 512×512 by the read cap). Callers are test-only today (tests/t_frame.cpp:503-532). Fix: bail when old == new; convert to an explicit stack/queue.
- L652-687 + L482-486: [error-handling][bug] `clip()` has no coherent failure contract: an out-of-range extent is folded into a 0×0 frame (L668-670, exercised by tests/t_frame.cpp:359) while a negative origin or over-wide explicit extent throws from `at()`/the ctor (documented as a "finding" by tests/t_frame.cpp:369); consequently `split()`'s `if (!frame)` null-check (L482-486) is dead — `clip` can never return null. Fix: return `nullptr` (or clamp) for all invalid extents, which also revives the split/explode error paths.
- L493-540, L542-562, L1005-1023: [bug] `draw()`, `save()` and `drawAt()` only test the upper bound (`dot.x + x < m_width` L503/L551; `bx + x >= m_width` L1015) — negative `dot.x/dot.y` (int, DotArray.h:33-34) or negative `bx/by` pass straight into `at()` which throws `std::out_of_range` (Frame.h:51); the pen loop then still indexes `dot.x + x` from the negative origin. Reachable via `CDotArray` if any producer emits negative dots (`setLimit` clamps upper only — needs verification of lineTab/circle edge cases); all callers test-only today. Fix: skip coordinates failing `isValid`.
- L446: [ub] `setTopPixelAsTranparency()` reads `m_rgb[0]` on a possibly empty vector — `CFrame(0,0)`/post-`clear()` frames make this an OOB read (operator[] is unchecked); test-only caller today. Fix: `if (m_rgb.empty()) return;`.

- L253, L394, L402: [ub] `USER_BMPHEADER` cast to `bmp + 2` (2 mod 4) and `png_OBL5`/`png_IEND` casts at arbitrary byte offsets after variable-size IDAT chunks are misaligned scalar-write UB; benign on the current LE x86/arm/wasm32 targets (same LE-only assumption flagged in the FrameSet audit) but UB the optimizer may exploit. - L390-399: [error-handling] the obLT injection trusts the caller's `obl5data` blob to be ≥ 20 bytes with a reserved trailing CRC slot (the sole in-repo caller, FrameSet.cpp:1323-1333, builds it correctly); a shorter blob yields `Length = toNet(size - 12)` wrapping unsigned and a CRC region of `size - 8` that underflows into nonsense. - L48-51: [dead] the "dimensions must be multiple of 8" check is an empty `if` body (LOGW commented out) — either restore the warning or delete the conditional; likewise the `(width & 7)` invariant is unenforced everywhere else (toPng/PngMagic pad-to-8 only in the reader, PngMagic.cpp:329-337).

- L449-459, L860-873: [algo] `hasTransparency()`/`isEmpty()` treat only alpha byte == 0x00 as transparent (pixels at alpha 0x01-0xFE count as opaque/empty-respecting) and scan with early-out on `m_width*m_height` int math — consistent with the ABGR convention (see Notes) but the enum-less magic masks (0xff000000 repeated at L866, L882, L906, L918, L969, L984) should use the declared `ALPHA_MASK`/`COLOR_MASK` so a future format change doesn't miss a site.

## Notes
- Pixel-format assumption verified end-to-end: the engine's canonical `uint32_t` is SDL `ABGR8888` (runtime.cpp:1765 converts to it before memcpy at :1778), i.e. little-endian memory layout R,G,B,A; therefore toBmp's `d[0]=s[2], d[2]=s[0]` (L277-279) and toPng's raw row memcpy (L311, ColorType 6) are **correct** on LE — both silently swap R/B on a big-endian build. Tests t_frame.cpp:299-319 pin the abgr2argb semantics.
- `abgr2argb`/`argb2arbg` (L964-990) intentionally zero the color bytes of fully-transparent pixels (the `if (t & 0xff000000)` gate) — matches tests (t_frame.cpp:308 "dropped, not swapped") and docs/bugs/coverage-round2-findings.md:107; intentional, not a bug.
- toPng byte math verified exact: 8 (sig) + 21+4 (IHDR via struct writes; `Lenght = 13`, CRC over type+data) + per-IDAT 12 overhead × ceil(cDataSize/32767) + obl5data + 12 (IEND) equals L330's formula; chunking loop count provably equals `cDataBlocks`. The theoretical cDataSize==0 under-allocation (cDataBlocks=0 but the do-while always writes one 12-byte IDAT) is unreachable because `compressBound`/`compress2` (helper.cpp:166-179) never produce an empty stream.
- `read()` is the strongest reader in this pair: it bounds-checks `compressedSize` against file size (L186), enforces `destLen == w*h*4` (L207, which the FrameSet audit points at as the good example), and validates the filler; `IFile::read/write` return `IFILE_OK`/`IFILE_NOT_OK` sentinels (FileWrap.cpp:71-85, FileMem.cpp:55-79), so all the `!= IFILE_OK` comparisons here are correct.
- Dimension caps cross-checked: ctor cap 4096 (L43) vs `MAX_IMAGE_SIZE=512` (ss_limits.h:21) used by read (L156) and write (L94) — a frame read from disk can never violate the ctor cap; the write-side 512/4096 round-trip asymmetry with FrameSet is already reported in docs/audits/FrameSet.cpp.audit.md (High, its L128-vs-L326 entry) and not duplicated here.
- Adjacent-file issue to route to the PngMagic audit (not counted here): PngMagic.cpp:338 constructs `CFrame(width,height)` from raw IHDR dimensions with no cap check, so a PNG claiming width>4096 throws `std::invalid_argument` uncaught on the same asset path as the explode finding; PngMagic.cpp:291-304 also `resize()`s metadata vectors by an unvalidated `obl5t.Count`.
- Suggested runtime verification: (1) parsePNG over a synthetic PNG whose obLT v0 chunk has `sum(sx) > width` and one with `sx=0x2000` — expect clean failure, today it terminates (run under ASan); (2) `CFrame f(4,4); std::vector<uint32_t> tiny(3); f.setRGB(tiny); f.hasTransparency();` — expect ASan heap-buffer-overflow; (3) `floodFill(0,0,c,c)` on any 8×8 frame with a small stack — expect SIGSEGV; (4) `shiftLEFT` on a 4×1 frame — expect it to actually shift; (5) stub `compressData` to return Z_MEM_FAILED and call `takeScreenshot` — expect a 0-byte screenshot file to be written today.
