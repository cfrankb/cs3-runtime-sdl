# Audit: src/shared/FileWrap.cpp
Date: 2026-11-17

## Summary
CFileWrap is a thin stdio wrapper whose disk-side `operator>>(std::string&)` length-prefix decoder is broken: it cannot parse the 32-bit length encoding that its own `operator<<(std::string_view)` emits (the `size == 0xffff` dispatch at L159 is dead because `size` at that point holds a single byte ≤ 0xff), so long strings round-trip corrupted and the 32-bit reader branch is unreachable. Next, zero-size `read`/`write` are reported as failures because `fread/fwrite(ptr, 0, 1)` return 0, which makes empty-string and zero-length transfers fail on the disk backend while the sibling CFileMem backend succeeds — a live divergence in the engine's main file-I/O class. The whole static in-memory file registry (`addFile`/`freeFiles`/`findFile` and every `m_memFile` branch) has no caller anywhere in the repo and is dead weight. Counts: 1 Critical, 3 High, 5 Medium, 5 Low.

## Findings

### Critical
- L154-171: [bug][dead] **FIXED 2026-11-17** (docs/bugs/resolved/critical-triage-2026-11-17.md BUG-C10; `test_ifile_string_tiers`). Original finding: disk string reader cannot decode the 32-bit length form the writer emits (L203-210): `size` holds the single marker byte (≤0xff) when L159 tests `size == 0xffff`, so the branch is always false and dead (L162-163 unreachable); a string ≥ 65535 bytes written by L203-210 is misread — L168 loads the 2-byte `0xffff` marker itself as the length (65535), then L173 slurps the real 4-byte length field as string data → silently corrupted string plus stream desync for the rest of the file. Fixed: reader decodes `uint8_t`/`uint16_t`/`uint32_t` locals mirroring the working FileMem.cpp logic, bounds the declared payload against remaining file bytes, and skips the payload `fread` for size 0 (empty strings now succeed on disk too).

### High
- L76, L84, L173, L213: [bug] zero-size transfers are misreported as failure: `fread(buf,0,1)`/`fwrite(buf,0,1)` return 0, so `read(buf,0)`, `write(buf,0)`, `file << ""`, `file >> empty_string`, and `+= ""` all return IFILE_NOT_OK/false on the disk backend even though the bytes (length prefix) are written correctly; CFileMem handles length 0 explicitly (FileMem.cpp L140, L173) so the backends diverge — e.g. a savegame with an empty name fails at gamemixin.cpp:1916/1936 (`_R(tmp.data(), 0)` / `_W(name.c_str(), 0)`); tests mask it because t_ifile.cpp L115-126 ignores the `<<`/`+=` return values. Fix: early `return IFILE_OK;` when `size == 0` in read/write, and guard the body transfer in the string operators (as FileMem does).
- L87-99: [leak] `open()` overwrites `m_file` (L96) without closing a previously open handle; reachable sequence: `CGameMixin::recordGame` opens member `m_recorderFile` "wb" (gamemixin.cpp:2008) and `playbackGame` reopens the same still-open member "rb" (gamemixin.cpp:2022) — no `close()` call on `m_recorderFile` exists anywhere in src/, so each record→playback switch leaks one FILE*/fd until the CGameMixin destructor. Fix: call `close()` at the top of `open()`.
- L71-85, L116-144: [error-handling][ub] no `m_file` null guard in `read`/`write`/`getSize`/`seek`/`tell`/the string operators — after a failed `open()` or after `close()` (which nulls `m_file` at L111) every method calls `fread`/`fwrite`/`fseek`/`ftell` on a null FILE* → segfault instead of a failure return; sampled call sites (runtime.cpp, helper.cpp, tileset_tex.cpp, etc.) all gate on `open()`'s return, but nothing enforces it (needs verification by auditing every caller). Fix: `if (!m_file) return IFILE_NOT_OK/false/-1;` in each.

### Medium
- L27, L40-59, and every `if (m_memFile)` branch (L73-74, 81-82, 90-93, 104-107, 118-121, 134-135, 143, 148-151, 184-185) plus FileWrap.h L29/62-63/68-71: [dead][shrink] the static in-memory registry is speculative infrastructure with zero callers — repo-wide grep (src, tests, itools) finds no call to `addFile`/`freeFiles` anywhere, so `m_files` is always empty, `findFile` always returns nullptr, and `m_memFile` is always nullptr at runtime; ~40 lines plus the FileMem dependency could be deleted (note: docs/audits/PngMagic.cpp.audit.md L15 assumes a "live container path via CFileWrap::open → findFile" — that premise is wrong; CFileMem is only used directly in tests/runtime.cpp/engine_hw.cpp, never injected through CFileWrap). Fix: delete the registry and branches, or add the caller that was intended.
- L96: [ub] `fopen(fileName.data(), mode.data())` requires both string_views to be NUL-terminated, which the type does not guarantee — a caller passing a substring/sliced view makes fopen read past the end; all 22 current call sites pass literals, `c_str()`, or `std::string` (guaranteed terminated), so this is a latent API trap on the engine's main open function. Fix: construct `std::string(fileName)` (and mode) or change the parameter type.
- FileWrap.h L67: [ub][leak] class owns a raw `FILE*` with no deleted/defined copy ctor or assignment (rule of three violation) — any copy yields double `fclose` of the same handle; no copy site found (all uses are locals or members, needs verification that CGameMixin is never copied). Fix: `CFileWrap(const CFileWrap&) = delete;` and delete `operator=`.
- L155-170, L190, L200, L206-209: [ub][algo] length-prefix I/O type-puns multi-byte integers straight through `fread`/`fwrite`/address-of (`fwrite(&size, 1, ...)` on a `size_t`, `fread(&size, 2, ...)` into an `int` whose high byte 0xff survives from the first read): correct only on little-endian hosts and silently corrupts on big-endian; combined with raw host-order int passthrough (L63, L68) all engine files are LE-only format. Fix: `memcpy` into `uint8_t/uint16_t/uint32_t` and (if portability matters) explicit little-endian encode/decode.
- L71-85: [error-handling] `fread(buf, size, 1)` "one item" semantics: a short read on a large buffer consumes the partial bytes but returns failure, leaving the stream mid-record so subsequent reads desync (e.g. t_ifile-style `read(buf, filesize)` on a truncated asset); no negative-size check either — a negative `int size` converts to a huge `size_t` and the partial-copy then overruns the caller's buffer. Fix: validate `size >= 0`, consider `fread(buf, 1, size, ...)` with byte-count return, or document all-or-nothing.

### Low
- L89: [error-handling] `m_mode` is assigned before the open attempt, so `mode()` reports the failed mode after a failed `open()` (FileMem.cpp:83 has the same shape); also `close()` on a never-opened object returns false (L103 `result = false`) while `CFileMem::close()` always returns true — sibling divergence.
- L124-127: [error-handling] `getSize()` ignores `ftell`/`fseek` return codes: if `ftell` fails (-1) the restore becomes `fseek(m_file, -1, SEEK_SET)` (fails, position left at EOF) and -1 is returned as a size; callers using it for allocation sizes get a nonsense value.
- L220-221: [ub] `memset(&b,0,1)` then reading one raw file byte into a `bool` can produce a non-0/1 bool representation (UB per the standard; fine on x86 in practice); read into a `uint8_t` and assign `b = v != 0` (FileMem.cpp L182 shares the pattern).
- L23, L24: [shrink] `#include <cassert>` and `#include "logger.h"` are unused in FileWrap.cpp (no assert/LOG* anywhere in the file); note also this is the engine's main I/O class yet contains zero logging on open/read/write failures despite the AGENTS.md LOGx convention.
- L56, L52-53 (IFile.h) / FileWrap.h L52-56: [algo] `getSize`/`seek`/`tell` use `long` and `read`/`write` use `int`: fine on LP64 Linux but a 2 GiB ceiling on LLP64/Windows builds for files and offsets, and the `int` return is reserved to 0/1 (IFILE_OK) so byte counts are never reported to callers.

## Notes
- Verified `addFile`/`freeFiles`/`findFile`/`m_files`/`m_memFile` have no callers repo-wide (grep of `*.cpp,h,hpp,ql` plus a filter-free grep) — the CFileMem-via-CFileWrap injection path has never been wired up. This means the PngMagic audit's L15 claim that negative-size `CFileMem::read` is reachable "via CFileWrap::open → findFile" is not currently true; the FileMem exposure comes only from direct CFileMem users (tests, runtime.cpp:2963, engine_hw.cpp:1176, itools/mapzutil).
- IFile contract (IFile.h L21-22): `read`/`write` return IFILE_OK=1 / IFILE_NOT_OK=0; FileWrap conforms on non-zero sizes. Callers throughout the engine (CGame, CMap, CActor, CFrameSet serializers via `read(IFile&)`/`write(IFile&)`) use `>>`/`<<`/`+=` on both backends, so any disk/mem divergence (empty strings, 32-bit lengths) breaks the FileWrap-vs-FileMem byte-comparison tests' premise.
- FileMem sibling facts callers should know (already-exposed, not re-audited): `CFileMem::close()` clears its buffer (FileMem.cpp L99), `open("w")` does not truncate (TODO at L90), `seek()` is unchecked — but none of this is reachable through CFileWrap today because of the dead registry.
- t_ifile.cpp L115-126 exercises empty-string `<<`/`+=` only via unchecked return values + `tell()`, so the zero-size false-failure is invisible to CI; the string round-trip test (`test_ifile_read_write`) only reads strings that exist in `annie.obl`.
- All 22 `open()` call sites observed pass NUL-terminated names and modes; no caller copies a CFileWrap; `m_recorderFile` is the only long-lived instance and is where the reopen leak lives.
- Suggested runtime verification: (1) round-trip `<<`/`>>` of `""` and of a 70 000-byte string through CFileWrap on a temp file — expect false return on the empty write body and a corrupted/garbage string on the long read; (2) run record→stop→playback twice under `lsof`/ASAN to confirm the reopened recorder FILE* leak; (3) ASAN run of `t_ifile` and a savegame with an empty name.
