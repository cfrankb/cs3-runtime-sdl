# Audit: src/shared/helper.cpp
Date: 2026-11-17

## Summary
helper.cpp is small and its zlib wrappers and `getUUID` are sound, but five of the eight declared functions (`toUpper`, `upperClean`, `copyFile`, `concat`, the raw-pointer `compressData`) have zero production callers — they exist only to be exercised by `tests/t_helper.cpp`, so most of the file is self-maintaining scaffolding. Inside that dead cluster, `copyFile`/`concat` ignore every `CFileWrap` read/write return value, so were they ever wired up, a short read or failed write would be reported as a successful byte-corrupted copy. The one production-reachable hazard is `readFile`'s size handling (`long` → `size_t` → `int` narrowing, unguarded `-1` from `getSize`). Counts: 0 Critical, 2 High, 4 Medium, 8 Low.

## Findings

### High
- L86, L90, L127, L129: [error-handling] `sfile.read`/`tfile.write` return values ignored in `copyFile`/`concat` — `CFileWrap::read`/`write` return `IFILE_OK(1)`/`IFILE_NOT_OK(0)` (FileWrap.cpp L71-85), so a mid-stream read failure leaves the value-initialized zero-filled `buf` copied verbatim and a write failure (disk full) is invisible, yet the function returns `true` with an empty errMsg; today test-only (see dead-cluster finding) but these are the repo's intended copy utilities. Fix: check `!= IFILE_OK` and set errMsg + `result = false`, as `readFile` L206 already does.
- L204-206: [bug][error-handling] `readFile` (production-reachable: level.cpp:55/83/178): `size_t size = file.getSize()` turns `getSize`'s possible `-1` (ftell failure, unchecked per FileWrap audit L26) into SIZE_MAX → `std::vector<uint8_t> data(SIZE_MAX)` throws uncaught `std::length_error`; that `size_t` then narrows into `IFile::read`'s `const int size` (IFile.h L45), so any file > 2 GiB passes a negative count. Fix: take `long sz`, fail early on `sz < 0`, and guard `sz > INT_MAX` until IFile widens. (Needs verification that `ftell` can fail on an opened "rb" stream — a directory path opened via glibc `fopen` is the candidate repro.)

### Medium
- L35-50, L77-152, L154-164 (+ helper.h L24, L26-27, L29): [dead][shrink] `toUpper`, `upperClean`, `copyFile`, `concat` and the raw-pointer `compressData` overload have zero production callers — repo-wide grep of src/, tests/, itools/, packages/, android-project/, backup/, cmake/ finds only the definitions and `tests/t_helper.cpp`; ~90 of 212 lines are kept alive by the test that covers them. The `compressData(vector)` overloads (Frame.cpp:121/315, FrameSet.cpp:155, layer.h:134), `getUUID` (FrameSet.cpp:99) and `readFile` (level.cpp) do have real callers. Fix: delete the five dead functions and their test blocks, or wire up the intended call sites; `toUpper`/`upperClean` additionally duplicate `std::transform`/`std::ranges::transform` + `std::isalnum`/`std::toupper`.
- L84-85, L90, L125-126, L129: [bug] `int size = sfile.getSize()` narrows `long` → `int`; a > 2 GiB file or a `-1` size becomes negative, and `std::vector<char> buf(negative)` constructs a huge `size_t` size → uncaught `std::length_error`/`bad_alloc` termination; the `int` then feeds `IFile::read`'s int parameter (the 2 GiB ceiling already flagged at FileWrap audit L29). Fix: use `long`/`size_t` locally and reject `size < 0 || size > INT_MAX` before allocating.
- L117, L131-141: [error-handling] `concat` opens the output "wb" (L117) and on a mid-list read failure breaks out (L138) leaving the partially-written output file on disk (closed at L141) — a corrupt bundle indistinguishable from a complete one to any later reader; `copyFile`'s failed-write branch (L88-100) leaves a truncated file the same way. Fix: on failure close and `std::remove` the output, or write to a temp name and rename on success.
- L26-32: [dead] the `USE_QFILE` → `QFileWrap` branch is never active: no CMakeLists.txt or build config anywhere in the repo defines `USE_QFILE`, so `#define FILEWRAP CFileWrap` is the only live branch; it is the same dead-flag pattern already flagged in gamemixin.h (docs/audits/gamemixin.audit.md L39). Fix: delete the `#if` here (and coordinate with the five other files using the flag).

### Low
- L37-42: [ub][perf] `toUpper` feeds raw `char` to `isalpha`/`toupper` — bytes ≥ 0x80 (UTF-8 paths/text) become negative ints, UB per the standard (glibc's table happens to accept −128..−1; other libcs crash), and the loop condition re-runs `strlen` every iteration (O(n²)); fix is moot once the dead-code removal lands, otherwise `static_cast<unsigned char>` + hoisted length, or one `std::transform`.
- L49: [error-handling] `upperClean`'s `isalnum`/`toupper` are locale-dependent: under a non-"C" locale, locale-specific letters pass the filter and uppercase differently, changing what sanitized identifiers downstream accept; the `int` parameter also admits out-of-range values (same UB class). All current callers (tests only) pass ASCII.
- L77, L113 (helper.h L26-27): [perf][shrink] pass-by-value parameters (`const std::string in`, `const std::string out`, `const std::list<std::string> files`) copy every path string and the whole file list per call; `const &` is free.
- L95-98, L104-107, L133-136, L145-148: [shrink] snprintf-into-`std::vector<char>` error-message scaffolding duplicated 4× (24 lines) where `errMsg = "couldn't read: " + in;` is one line each.
- L204-210: [error-handling] `readFile` cannot distinguish an empty file from failure: `CFileWrap::read(buf, 0)` returns `IFILE_NOT_OK` (zero-size quirk, already reported at FileWrap audit L13), so a legitimate 0-byte file logs "can't read data" and returns `{}` — identical to a missing file — and level.cpp:55/83/178 callers proceed on the empty vector.
- helper.h L22: [shrink] `#include <list>` duplicated at L20 and L22.
- src/level.h L25: [shrink] re-declares `std::vector<uint8_t> readFile(const char *)` at global scope — same function as helper.h L32; a future one-sided signature change is a silent ODR violation (bossdata.cpp:339 further defines an unrelated local `readFile(const char*, std::string&)`, confusing readers and greps). Fix: include `shared/helper.h` from level.h and drop the duplicate.
- L52-75: [error-handling] `getUUID` trusts `std::random_device` entropy; pre-GCC-12 libstdc++ on MinGW historically returned deterministic values (GCC bug 86342), which would make v4 UUIDs written into `.obz` tags (FrameSet.cpp:99) collide on a Windows build with that toolchain (needs verification whether any shipped Windows target uses it). The `UUID_BUFFER_SIZE=40` buffer fits the 36+NUL output exactly — no truncation.

## Notes
- Caller census (grep, whole repo incl. itools/packages/android-project/backup): live — `getUUID` (FrameSet.cpp:99), `compressData(vector<uint8_t>)` (Frame.cpp:121, 315; FrameSet.cpp:155), `compressData(vector<uint16_t>)` (layer.h:134), `readFile` (level.cpp:55, 83, 178; tests t_map.cpp:460, t_maparch.cpp:328/357). Dead outside `tests/t_helper.cpp` — `toUpper`, `upperClean`, `copyFile`, `concat`, raw-pointer `compressData`.
- IFile contract (IFile.h L21-22): `read`/`write` return `IFILE_OK`/`IFILE_NOT_OK`, never byte counts — `!= IFILE_OK` (the `readFile` L206 pattern) is the only valid success check; `t_helper.cpp`'s byte-identical round-trips (L64-136) cannot surface ignored-failure paths on a healthy disk.
- `compressData(vector<uint16_t>)` L188-189 compresses raw host-endian tile bytes, little-endian-only on disk — consistent with the engine-wide LE format noted in the FileWrap audit; intentional, not flagged.
- All three `compressData` overloads handle empty input correctly (`compressBound(0)` = 12, zlib accepts a null `data()` pointer with size 0); the L176/L191 shrink-resizes are correct. The raw overload's `new[]` at L157 requires caller `delete[]` even when `compress2` fails — ownership is documented only in a `t_helper.cpp:182` comment, another reason to delete it.
- `getUUID` output format, v4/RFC-4122 bit marking (L63/L65), and buffer sizing were verified correct (36 chars + NUL ≤ 40); tests already cover format + 100-sample uniqueness.
- Deleting the dead functions requires removing the matching blocks in `tests/t_helper.cpp` (registered via `tests/tmain.cpp`) per AGENTS.md dead-artifact conventions.
- Suggested runtime verification: (1) call `readFile("some_directory")` and `readFile` a 3 GiB sparse file under ASAN to exercise the `getSize`/narrowing paths; (2) run the `copyFile` test with `ulimit -f` set low to confirm the silent-success write failure; (3) grep CI build logs to confirm no `-DUSE_QFILE` ever reaches the compiler.
